Packing System
AmiT / AceMicromatic MIT - Oct' 24
Sections
Overview Highlights
Making three separate systems — handheld, portal, API — behave like one.
Context: Every box leaving the warehouse depended on a chain of manual entries — scan the part, type the pallet, print the label — each step a chance to mis-key a code and send a shipment to the wrong truck. Operators used Zebra handhelds, managers used a desktop portal, and the two never agreed in real time.

My role: I owned the full stack — Flutter handheld UI and hardware driver integration, Blazor portal, and the ASP.NET API — working alongside a logistics engineer who defined the packing workflows and label formats.

Approach: I built the Packing System as three layers: a Flutter handheld app for operators, a Blazor web portal for management, and an ASP.NET 6 API tying them together. I integrated native hardware protocols — Zebra DataWedge for barcode capture and ZSDK for on-the-fly label printing — so operators scan and print with zero perceived latency. The API orchestrates pallet-to-box mapping and pushes status to an "Andon" display that gives management real-time visibility into the packing line.

Key decision — split apps over one unified app: The operator experience is a handheld-tuned Flutter app while management gets a browser portal, rather than one app trying to serve both. A single app would force either a desktop UI onto a 4-inch scanner screen or a mobile UI onto a wall-mounted monitor; the split lets each surface optimize for its input method while sharing one API. Inside that split, the handheld talks REST rather than SignalR — Zebra devices drop persistent connections in power-saving mode, so optimistic UI updates plus a background sync worker proved more reliable than maintaining a circuit on a mostly-sleeping device.

Impact: 90% fewer manual entry errors — a chaotic warehouse floor turned into a data-driven operation.
